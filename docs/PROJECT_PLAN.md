# Memoir AI 개발·완성 계획

제품 목표·첫 완료 기준·개발 순서의 원본 문서. 2026-10-23 회고록 중심 목표를 반영했다. 아래 목표는 구현 완료나 운영 성과 보고가 아니며, 현재 동작은 코드와 실행 증거로 확인한다.

## 목표

**Memoir는 일기·스크랩·대화를 시간 흐름으로 엮어, 자신의 경험과 생각의 변화를 돌아보고 직접 고쳐 쌓아 가는 개인 회고록 서비스다.** 저장한 자료를 다시 찾는 기능은 회고를 돕는 기반이며, 검색이나 AI 요약만으로 제품 완료를 판정하지 않는다.

일상 기록 → 시기·주제별 회상 → 당시 기록과 관련 자료 확인 → 회고 초안 → 사용자 편집·저장 → 재접속 후 이어 쓰기까지 실제 백엔드로 연결한다. 주간·월간 회고부터 시작하고, 축적한 회고를 장기적인 삶의 이야기로 확장할 수 있도록 한다.

### 첫 사용자 과제

“지난 한 달 동안 무엇을 겪고 어떤 생각이 달라졌는지, 내 일기와 읽은 자료를 보며 내 말로 남기고 싶다.”

사용자는 기간·주제를 정하고 일기·스크랩에서 관련 기록을 고른다. AI는 기록에 근거한 초안과 회고 질문을 제안한다. 기록에 없는 사건·감정·동기·인과를 사실처럼 채우지 않고, 해석과 확인할 질문을 구분한다. 작성자 본인이 초안을 고치고 승인한 내용이 회고록에 저장된다.

### 첫 완료 흐름

1. 로그인 후 자신의 일기와 스크랩을 저장하고 처리 상태를 확인한다.
2. 기간·주제로 기록을 돌아보고 필요한 원문을 다시 연다. 사건이 일어난 날짜와 기록을 작성·수정한 날짜를 구분한다.
3. 자료를 근거로 회고 초안을 만들고, 각 사실의 원기록과 미확인 내용을 확인한다.
4. 초안을 자신의 말로 수정·저장한다. 원기록, AI 제안, 사용자 최종 서술을 구분해 보존한다.
5. 재접속해 저장한 회고를 읽고 수정하거나 다음 회고에서 이어 쓴다. 기록 수정·삭제가 관련 검색과 향후 생성에 반영된다.

### 제품 KPI — 초기 목표, 달성 실적 아님

- **회고 완성:** 사전 등록한 회고 업무 5건 중 4건 이상에서 개발자 대행 없이 기록 선택 → 근거 확인 → 초안 생성 → 사용자 편집·저장 → 재접속 후 이어 쓰기를 완료. 5건은 기간·주제·입력 기록과 기대 산출물이 구별되는 과제로 등록한다.
- **회상·재발견 품질:** 답과 필요한 근거를 사전 정의한 자기 기록 질문 10건 중 8건 이상에서 필요한 원기록을 찾아 확인. 원문과 다른 내용을 답하면 성공으로 세지 않는다.
- **실제 재사용:** 초기 사용자 5명 중 3명 이상이 첫 회고를 마친 뒤 7일 내 다른 날에 돌아와 기록을 추가하거나 회고를 편집·이어 쓴다. 기간의 시작은 첫 회고 저장 시점이며, 첫 과제를 완료하지 못한 참여자도 분모에 남긴다. 빈 페이지 열람·데모 방문·운영자 점검은 제외한다.
- **사용자 소유권:** 저장한 회고의 내용·근거·수정 이력을 확인하고 다시 편집할 수 있다. 자동 초안 생성이 원기록이나 사용자 최종 글을 조용히 덮어쓰지 않는다.

평가 전에 허용 입력·권한·지원 환경·작업 시간 상한·완료 기준을 고정한다. 개발자가 대신 자료를 정리하거나 글을 써서 끝내면 독립 완료로 세지 않는다. 정상 중단·제품 오류·사용 중단과 개입 이력을 남기며, 시작 후 실패한 과제를 분모에서 빼거나 쉬운 과제로 교체하지 않는다. 질문 10건과 과제 5건의 기준·버전을 남기고, 회고의 길이나 긍정적인 문체를 품질로 대신하지 않는다.

### 품질·운영 가드레일

- 사전 고정한 정상·경계 검수셋 최소 20건에서 다른 사용자 자료 노출, 원기록 오연결, 기록에 없는 사건·감정의 사실화, 사용자 글 무단 덮어쓰기 같은 치명 오류 0건을 요구한다. 검수셋의 관측 결과를 전체 환경 무결점 보장으로 쓰지 않는다.
- AI 초안이 기록에 근거했다고 주장하는 사실은 원기록·버전으로 100% 연결한다. 사용자의 새 서술과 AI 해석·질문은 따로 표시하며, 불확실하거나 상충하는 기록을 확정된 기억으로 합치지 않는다.
- 수정·삭제 후 색인·관계·요약·초안 문맥을 점검한다. 사용자에게 이미 저장된 회고의 영향과 처리 상태를 알리고, 과거 사용자 글을 자동 재작성하지 않는다. 검색 제공에서의 삭제와 백업 보존/만료 정책도 구분한다.
- 재접속·재시작·재배포 뒤 원기록과 회고가 보존되고, 백업·복구를 실제로 확인한다.
- 기록 등록·처리·검색·근거 열람·회고 편집/저장 이벤트와 실패·재처리를 관찰한다. 지연·복구 시간·사용자당 비용은 실제 측정 뒤 운영 상한을 정한다. 일기 본문과 민감한 대화 내용을 일반 로그에 남기지 않는다.

### 설계 우선순위

달력은 회상할 시기를 고르는 입구, 검색은 원기록을 찾는 수단, 그래프는 시기·사람·주제·사건과 관련 자료의 연결을 탐색하는 수단으로 둔다. 관계가 있다는 사실만으로 심리나 사건의 원인을 단정하지 않는다. GraphDB의 가치는 같은 과제에서 기존 검색 대비 회상·원문 확인·회고 작성에 어떤 차이를 만드는지 비교한다.

첫 범위에서는 자동으로 일생 전체를 완성하는 자서전, 근거 없는 성격/감정 진단, 타인 기록 추측, 사용자 승인 없는 외부 공개를 넣지 않는다. 실제 사용자 기록과 샘플/합성 입력을 구분하고, 목표 KPI와 측정한 결과를 별도 기록한다.

## 현재 상태

- React·FastAPI·Supabase·Kuzu·LangGraph를 활용한 구현과 테스트·CI 구성이 있다. 실제 동작 범위는 현재 브랜치의 코드와 실행 결과로 확인한다.
- 공개 샘플 화면과 준비된 응답은 실제 백엔드·LLM 연동의 완료 근거로 사용하지 않는다.
- 실제 서비스 배포·운영은 완성되지 않았다. README 설명과 코드가 다르면 실행 경로를 확인하고 문서를 정정한다.

## 작업 순서

1. 브랜치·작업 트리·저장소 지침을 읽고 사용자의 기존 변경을 보존한다. 현재 기능, 재현한 오류, 우선순위를 먼저 보고한다.
2. 기존 CI의 Python 3.11·Node 20 및 잠금 파일을 기준으로 실행 환경을 확인한다. 다른 버전을 사용한다면 호환성을 검증한다.
3. 필요한 환경변수 이름과 설정 방법을 정리한다. 비밀값은 커밋·로그·문서에 넣지 않고 Supabase service-role 키를 프론트엔드에 노출하지 않는다.
4. 데모 경로와 실제 경로를 구분해 인증·일기·스크랩·검색·LLM 응답을 점검한다. 외부 의존성을 연결하지 못했다면 모의 테스트 결과와 실제 연동 결과를 구분한다.
5. 재현된 문제부터 작은 변경으로 수정하고 관련 테스트·린트·빌드를 실행한다. 핵심 흐름이 동작하기 전에 에이전트나 기능을 늘리지 않는다.
6. 배포 후보별 비용·설정·데이터 영속성·운영 부담을 비교한다. AWS를 전제로 정하지 않는다. 유료 자원 생성과 외부 공개는 사용자와 범위를 확인한다.
7. 사용자별 접근 제어와 검색 데이터 격리를 확인한다. Kuzu 데이터의 재시작·재배포 보존, 백업·복구를 검증한다. /tmp/kuzu_data 같은 임시 경로만으로 영속성을 보장했다고 쓰지 않는다.
8. 요청 제한, 모델 호출 비용, API 실패 처리와 로그를 점검한다. 실제 기록으로 대표 질문·정답 근거를 만든 뒤 검색과 답변을 평가한다.
9. 사용 가능한 버전을 배포하고 실제 사용 피드백을 받아 개선한다. 사용자 수·평가 결과는 측정 기간, 표본, 계산식을 함께 기록한다.

## 완료 기준

- 실제 인증·기록 저장·검색·근거 답변과 회고 초안 → 사용자 편집·저장 → 재접속 후 이어 쓰기 흐름을 확인한다.
- 다른 사용자의 데이터가 보이지 않고 재접속·재시작·재배포 이후에도 데이터를 보존하거나 복구할 수 있다.
- 실패 상황에서 확인 가능한 오류와 로그가 있고 관련 테스트·빌드가 통과한다.
- 배포 주소, 확인한 동작, 미해결 문제와 재현 방법을 기록한다.
- 앞의 회고 완성·재발견·재사용 목표와 가드레일을 사전 등록한 기준으로 측정한다. 측정하지 않은 항목은 미측정으로 남긴다.

모의 응답, 테스트 통과, 실제 연동, 운영 성과를 구분해 보고한다. 실제 사용자 일기·회고·인증 정보는 저장소에 넣지 않는다.
